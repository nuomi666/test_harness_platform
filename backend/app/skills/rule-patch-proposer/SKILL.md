## 一、能力定位

需求迭代时，业务规则文档（`references/*.md`）需要跟着变。直接让模型「重写整份规则文件」会带来
**编号漂移**（R/S 是分片生成、编号自检、受影响范围识别的公共锚点）、**静默丢规则**、
**格式漂移导致静默降级**、**无审阅难回滚**等问题。

本 Skill 只产出**定点补丁**，不重写全文：

| 操作 | 含义 | 约束 |
|---|---|---|
| `add` | 新增一条规则 | 编号续号（现有最大 +1），不允许插号 |
| `modify` | 修改某条规则的某一列 | 编号不可改；一次只改一列 |
| `deprecate` | 标记某条规则已废弃 | 不物理删行（保留编号可追溯） |

## 二、工作流

1. 读取目标页面的规则文件全文（由上游按 `biz_module + page` 精确取回，保证全文可信）
2. 读取本次「变更确认书」= 变更描述 + 用户对影响面分析疑点的确认答复
3. 逐条比对：现有规则是否被本次变更覆盖/冲突/失效？是否出现全新的业务规则？
4. 产出 JSON 补丁列表（`op / rule_id / table / field / cells / old / new / reason`）
5. 交由人工在界面上逐条确认后才落盘（落盘前自动备份，落盘后热重载知识库）

## 三、输出格式

只输出一个 JSON 对象：

```json
{
  "summary": "一句话说明本次补丁依据",
  "patches": [
    {"op": "add", "table": "R", "cells": ["规则名", "描述", "P1", "1", "覆盖要求"], "reason": "依据变更第X条"},
    {"op": "modify", "rule_id": "R3", "field": "覆盖要求", "old": "改动前原文", "new": "改动后完整内容", "reason": "依据变更第X条"},
    {"op": "deprecate", "rule_id": "R7", "reason": "功能已下线"}
  ]
}
```

### 各表 cells 顺序（必须与表头对齐）

| 表 | 前缀 | 表头（编号列由系统分配，cells 不含编号） |
|---|---|---|
| 核心业务规则 | R | 规则名 / 描述 / 等级 / 必生成数 / 覆盖要求 |
| 状态流转 | S | 状态流转 / 触发操作 / 前置 / 等级 / 覆盖要求 |
| 字段约束 | F | 字段 / 控件 / 必填条件 / 长度、字符集 / 说明 |

## 四、使用约束

1. **编号只增不改**：`modify` 的 field 不得是「编号」列；新增一律续号。
2. **无依据不提补丁**：变更确认书没提到、现有规则也没冲突的，一律不动。
3. **不输出完整规则文件**：只输出补丁；正文由系统定点替换生成。
4. **`old` 必须是从规则文件里摘的原句**，供人工核对改对了位置。
5. 若本次变更不需要任何规则调整，输出 `{"summary": "无需调整", "patches": []}`。

## 五、示例

变更确认书：「卡BIN池页面新增筛选区默认状态记忆，且筛选无结果时展示空态文案。」

```json
{
  "summary": "新增两条筛选区/空态相关规则",
  "patches": [
    {"op": "add", "table": "R", "cells": ["筛选区默认状态", "筛选区默认收拢，展开后输入框为空、下拉为“全部”", "P2", "1", "正向：首次进入页面为收拢态1条"], "reason": "变更第1条"},
    {"op": "add", "table": "R", "cells": ["列表空态文案", "筛选无结果时展示“暂无数据”占位图", "P2", "1", "正向：筛选无结果展示空态1条"], "reason": "变更第2条"},
    {"op": "modify", "rule_id": "R6", "field": "覆盖要求", "old": "正向：编辑保存后更新时间刷新+创建时间不变", "new": "正向：编辑保存后更新时间刷新+创建时间不变；异常：保存失败时更新时间不变", "reason": "变更涉及保存失败分支"}
  ]
}
```
