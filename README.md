# 测试管理平台（Test Management Platform）

> 基于大语言模型 + 向量知识库的测试资产管理平台：一级导航按功能域组织（用例生成 / 用例资产 / 报告中心 / 规则管理，并为 UI 自动化、接口自动化预留），覆盖需求评审 → 测试用例生成 → 质量评审 → 资产沉淀复用全流程。

---

## 一、项目简介

本平台面向测试团队，旨在解决传统测试用例编写效率低、经验难以沉淀、新人上手慢的痛点。通过大模型结合业务领域知识库，一键生成高质量的需求评审报告与测试用例，并支持资产沉淀与复用，持续提升生成精准度。

### 核心价值

- **提效**：需求输入后分钟级输出完整测试用例，覆盖正常、异常、边界全场景
- **沉淀**：优秀用例 / 评审模板一键沉淀到知识库，团队经验可复用、可传承
- **隔离**：按业务模块划分知识库，不同领域生成结果精准匹配业务规则
- **扩展**：插件化架构，可无缝扩展接口自动化、性能测试、UI 测试生成能力

---

## 二、核心功能

### 1. 四种生成模式

| 模式 | 入口接口 | 适用场景 | 流程说明 |
|------|----------|----------|----------|
| 快速模式 | `/generate-direct` | 简单需求、快速产出用例 | 输入需求描述 → 一键生成测试用例 |
| 评审模式 | `/review-only` | 需求正式评审前 | 上传文档 + 输入需求 → 生成专业需求评审报告 |
| 完整模式 | `/generate-review` → `/generate-cases` | 正式项目全流程 | 上传文档 → 需求评审 → 生成用例 → 补充优化 → 沉淀资产 |
| **增量迭代模式** | `/analyze-impact` → `/generate-incremental` | **历史页面有需求变更** | 召回历史用例 → 影响面分析 → 用户确认 → 基于变更合并新全量用例 → 沉淀覆盖 |

> 增量模式的"增量"指**变更驱动**，**不是"只产增量 delta"**。最终产物始终是该页面**全量**用例（详见 §三.6 用例分片生成）。

### 2. 多格式导出

- 支持导出 Markdown 源文件
- 支持导出 Excel 标准用例表格（自动解析 Markdown 表格，带边框、表头加粗、列宽自适应、首行冻结）
- 支持导出 Word（.docx）标准文档，用例渲染为带边框表格
- 支持导出 TXT 纯文本格式
- 导出表头自动识别模型实际输出的列名与列数，不会因列数变化而丢列
- 导出文件命名规范，可直接用于测试管理平台导入

### 3. 两级知识库沉淀

- **项目历史库**：沉淀到对应业务模块，仅本模块生成时召回复用，适合项目专属规则
- **通用技能库**：沉淀为团队通用模板，全团队所有场景均可复用，适合通用方法论、行业标准规则

沉淀采用「选择类型 + 确认按钮」二次触发机制，避免误操作沉淀无效资产。

**沉淀后召回**：所有需要产出用例/评审的流程（快速 / 完整 / 增量 / 差异分析 / 需求评审）都会**自动按 `(biz_module, page)` 维度语义召回历史沉淀资产**作为大模型参考上下文，仅供业务逻辑参考、不照搬其表格结构。增量模式**强制走召回**（先按 `history_version` 精确查元数据，兜底向量 top-K 3 条），无历史时会降级为全量生成并日志告警。

### 4. 业务模块隔离

内置商户模块、密钥模块、卡 BIN 模块等业务领域。生成时指定模块，向量检索仅召回对应领域知识，避免跨领域干扰。新增模块零代码配置，前端加一行配置即可生效。

### 5. 迭代优化能力

- 支持补充业务规则、纠错说明后重新生成用例
- 大模型基于补充内容定向优化，保留原有正确用例，修正不符合规则的部分
- 支持多轮迭代，直到用例完全符合业务预期

### 6. 文档上传辅助

- 支持上传 TXT、MD、PDF、DOCX 等格式需求文档，自动解析后拼入 Prompt 一起传给大模型
- 支持上传 PNG / JPG 等页面截图，通过 OCR 自动提取图中文字参与生成（需安装 `pytesseract` + `Pillow`）
- 快速模式、评审模式、完整模式均支持上传资料

## 三、框架架构与实现原理

### 整体架构

采用前后端分离 + 插件化 Skill 架构，核心分为五层：
```plain
┌───────────────────────────────────────────────────┐
│                  前端交互层 (React)                │
│  模式选择 / 需求输入 / 结果展示 / 导出沉淀         │
└───────────────────────────────────────────────────┘
                              ↓
┌───────────────────────────────────────────────────┐
│               API服务层 (FastAPI)                  │
│  接口路由 / 参数校验 / 统一异常处理 / 文件流响应    │
└───────────────────────────────────────────────────┘
                              ↓
┌───────────────────────────────────────────────────┐
│              核心调度层 (FlowScheduler)            │
│  流程编排 / Skill链执行 / 并行调度 / 超时重试      │
└───────────────────────────────────────────────────┘
                              ↓
┌───────────────────────────────────────────────────┐
│             能力插件层 (Skill Plugin)              │
│  需求评审Skill / 用例生成Skill / 可扩展更多Skill   │
│  统一基类：超时控制、自动重试、优先级、状态上报     │
└───────────────────────────────────────────────────┘
                              ↓
┌───────────────────────────────────────────────────┐
│            基础设施层 (Infrastructure)            │
│  大模型客户端 / 向量知识库 / 上下文管理 / 文件导出 │
└───────────────────────────────────────────────────┘
```
### 核心实现原理
#### 1. 插件化 Skill 架构

- 所有生成能力均继承 `BaseSkill` 基类，天然具备**超时控制、自动重试、优先级排序、状态上报**能力
- 新增业务能力只需新建一个 Skill 文件，实现 `get_prompt()` 和 `parse_output()` 两个方法即可接入调度器
- Skill 之间完全解耦，支持串行链执行、并行批量执行

**SKILL.md 与 references 的分工**：

| 维度 | SKILL.md（如 `req-test-cases/SKILL.md`） | references/*.md |
|---|---|---|
| 数量 | 每个 skill **一份** | 每个 skill **多份**，按模块/页面组织 |
| 作用 | 定义 Skill **自身**的工作流、输入输出规范、不可违反约束 | Skill 执行时按需加载的**业务规则素材** |
| front matter | `name` / `description` / `allowed-tools` | `biz_module` / `rule_scope: common\|module` / `priority` / `page` |
| 加载到 | `harness_skills`（技能库） | `harness_business_docs`（业务文档库） |
| 变更频率 | 扩能力时改 | 业务变更时频繁增减 |

类比：`SKILL.md` 像工具说明书（怎么用、输出什么格式），`references` 像工具的零件库（按需组装）。
**修改边界**：扩能力 → 改 SKILL.md；扩业务 → 增删 references 下的文档；两者互不干扰。

#### 2. 向量知识库双库设计

基于 ChromaDB 构建两级向量库，实现语义级召回：

- **通用技能库**：存放团队通用的测试方法论、行业规范、通用用例模板，全场景可召回
- **项目历史库**：按业务模块分区，存放沉淀的项目级用例、评审报告，同模块生成时优先召回
- 检索支持按 `biz_module` 过滤，确保生成结果匹配对应业务领域规则

#### 3. 通用规则强制注入机制

通用交互规则（如后台列表页的查询 / 重置 / 分页 / 空数据等校验项）与用户需求描述的语义距离较远，
若仅依赖 top-K 语义召回极易漏召，导致生成的页面用例缺失通用校验项。

因此规则文档通过 Front Matter 标记作用范围，加载器按标记分流处理：

```yaml
---
name: page_common_rules
biz_module: all       # all = 全模块通用
rule_scope: common    # common = 通用规则（强制注入）｜ module = 模块专属（语义召回）
priority: 100         # 优先级，数值大者优先拼装
---
```

- **通用规则**：检索时全量强制注入 Prompt，不参与 top-K 竞争，保证不漏
- **模块专属规则**：仍走语义召回，按 `biz_module` 过滤，精准匹配当前业务领域
- 生成时按「通用规则 → 模块专属规则 → 输出格式样例」的顺序拼装，冲突时高优先级覆盖低优先级

#### 4. 多流程上下文隔离

- 每次生成任务分配唯一 `flow_id`，全链路数据基于 flow_id 隔离存储
- 上下文管理器统一管理需求文本、评审结果、用例结果、补充规则等全链路数据
- 支持多用户、多任务并发执行，互不干扰

#### 5. 统一文件导出引擎

- 统一导出入口，支持 Markdown、Excel、Word、TXT 多格式
- Excel 导出自动解析 Markdown 表格，生成带边框、表头加粗、列宽自适应的标准文件
- 前端通过 Blob 流接收，自动处理文件名与后缀，解决 Excel 乱码问题

#### 6. 用例分片生成（编号分治）

业务规则条目超过一定数量时，让大模型一次输出全部用例极易触发**默认输出上限**导致截断。框架采用「**编号分治 + 条目级业务态约束**」：用 R（核心业务规则）/ S（状态流转）编号把规则条目化，按编号切片多次调 LLM，每片只负责若干编号，最后合并为单一全量表格 + 单一编号覆盖自检表。

**编号语义**：

| 编号 | 含义 | 是否参与分片 | 示例 |
|---|---|---|---|
| **R** | 核心业务规则（每条独立可校验的约束 = 1 个 R） | ✅ 参与 | R1 BIN区间唯一性、R6 更新时间自动维护 |
| **S** | 状态流转（每个"X → Y"的状态变化点 = 1 个 S） | ✅ 参与 | S1 使用中→已弃用、S3 待发布→已发布 |
| **F** | 字段约束（字段级元数据：必填/长度/字符集） | ❌ 不参与，全文注入每片 prompt | F1 LowBin、F3 MinPanLen |

**编号标记规则**：
- **必须用大写 R 或 S 开头的字母数字编号**（R1、R2、S1 等），提取正则 `\b([RS])(\d+)\b`，其他字母不被识别为分片单位
- F 不强制编号；字段校验直接写在 R 规则里也行，F 主要为「字段密集型表单」提供元数据维度

**分片自动判断**（你**无需手动决定**分不分片）：

| 业务规则文档状态 | 框架行为 |
|---|---|
| 没有 R/S 编号（简单页面 / 自由文档） | 不分片，单次全量生成 |
| 编号 1~`SEGMENT_SIZE` 条（默认 6） | 不分片，单次生成 + 编号覆盖自检表 |
| 编号 > `SEGMENT_SIZE` 条 | 自动分片：通用交互独立成片 + 编号均分 → 合并为单一全量表格 + 单张自检表 |

`SEGMENT_SIZE` 默认 6，可用环境变量 `LLM_SEGMENT_SIZE` 覆盖。**通用交互用例（查询/分页/重置等）独立成片**，避免与专属业务用例挤在同一片触发默认输出上限截断。

**实用建议**：
- 简单页面（3~5 条规则、无状态流转）→ 自由写，不打 R/S → 自动不分片
- 中等页面（6~10 条）→ 打 R 编号 1~6 → 不分片，有自检表
- 复杂页面（>10 条、有状态流转）→ 打 R + S → 自动分片

参考样板：`backend/app/skills/req-test-cases/references/card-bin/pool_page_rules.md`。

## 五、快速开始

### 环境要求

- Python 3.10+
- Node.js 16+
- 可用的大模型 API 服务（支持 OpenAI 兼容协议）

### 1. 后端启动

```
# 1.1 复制环境变量模板，填入你的 LLM 凭据
cp .env.example backend/.env
# Windows 用：copy .env.example backend\.env

# 1.2 创建虚拟环境（建议在项目根创建，便于前后端共享）
cd backend
python -m venv ../.venv
# 或 python -m venv .venv       # 仅在 backend 下创建

# 1.3 激活虚拟环境
../.venv\Scripts\activate       # Windows (项目根 venv)
# 或 .venv\Scripts\activate     # Windows (backend 下 venv)
# 或 source ../.venv/bin/activate # Linux/macOS

# 1.4 安装依赖（必需）
pip install -r requirements.txt

# 1.5 （可选）安装 OCR 引擎 - 图片文字识别
#    Python 包已写入 requirements.txt（pytesseract + Pillow）
#    但还需要本机安装 Tesseract 引擎：
#      Windows: https://github.com/UB-Mannheim/tesseract/wiki 下载安装
#      macOS:   brew install tesseract tesseract-lang
#      Linux:   sudo apt install tesseract-ocr tesseract-ocr-chi-sim
#    安装后打开 backend/app/utils/image_ocr.py
#    取消注释并修改 pytesseract.pytesseract.tesseract_cmd 路径
#    未安装时图片上传走降级逻辑，不影响其他功能

# 1.6 启动服务
cd backend
python -m uvicorn app.main:app --reload --port 8000
```

> 💡 **为什么用 `python -m uvicorn` 而不是 `uvicorn`？**
> `python -m` 方式直接通过 python 解释器加载模块，**不依赖 `.venv/Scripts/uvicorn.exe` 启动器**，
> 经过项目迁移后这些 exe 里的绝对路径会失效（报 `Fatal error in launcher`），`python -m` 方式永远可靠。

第一次启动会加载技能知识库（约 5-15 秒），看到
`✅ 平台启动完成 | 代码/文档分离 + 重试/超时/优先级 + 前端状态展示`
即表示服务就绪。

启动成功后访问：[http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs) 可查看接口文档

### 2. 前端启动

```
cd frontend

# 安装依赖（首次启动需要）
npm install

# 启动开发服务
npm start
```

启动成功后访问：[http://localhost:3000](http://localhost:3000) 即可使用平台

### 3. 常见问题

| 问题 | 排查 |
|---|---|
| `ModuleNotFoundError: No module named 'xxx'` | 确认 pip install 时所在的是已激活的 venv，pip 列表里能看到该包 |
| `Fatal error in launcher: Unable to create process` | **项目被迁移过**，`pip.exe`/`uvicorn.exe` 启动器写死了旧路径。改用 `python -m pip` / `python -m uvicorn` 即可，或用 `python -m pip install --force-reinstall --no-deps pip uvicorn` 重建启动器 |
| LLM 调用 401/403 | 检查 `backend/.env` 的 `LLM_API_KEY` 是否正确、未过期 |
| 启动卡在 `ReadTimeoutError: huggingface.co` | 本机可能访问不了 huggingface。确认 `backend/.env` 里 `USE_SENTENCE_TRANSFORMERS=1` 且 `HF_HUB_OFFLINE=1`，走本地模型缓存 |
| 上传图片但前端拿到空内容 | 需装 Tesseract 引擎，参见 1.5 |
| 端口 8000 被占用 | 启动参数改 `--port 8001`，前端同时改 `src/api.js` 的 `request.defaults.baseURL` |

## 六、使用指南

### 快速模式生成用例

1. 选择「快速模式（直接生成用例）」
2. 选择对应业务模块（可选，提升精准度）
3. 输入需求描述，点击「生成测试用例」
4. 生成完成后可补充规则重新生成，或下载、沉淀用例

### 评审模式生成报告

1. 选择「评审模式（仅生成评审报告）」
2. 上传需求文档 / 截图（可选）
3. 选择业务模块，输入需求描述
4. 点击「生成评审报告」，生成后可导出或沉淀

### 完整模式全流程

1. 选择「完整模式」
2. 上传资料、选择模块、输入需求
3. 第一步：生成需求评审报告，确认无误后进入下一步
4. 第二步：基于评审结果生成测试用例
5. 补充优化后，沉淀到知识库

### 增量迭代模式

适用于**已有沉淀基线的页面发生需求变更**的场景：

1. 选择「增量迭代模式」
2. 选择业务模块 + 页面（必须是已沉淀过基线的页面）
3. 输入变更说明（描述本次改了哪些规则）
4. 点击「分析影响面」→ 后端调用 `req-review-associator` 产出影响范围（受影响的模块、历史用例、回归范围）
5. **确认影响面无误** → 点击「生成增量用例」→ 后端召回历史 → LLM 出变更部分 → LLM 合并为新全量用例
6. 落盘产物在 `outputs/{slug}-test_cases.md`，**手动修改后可再次沉淀覆盖基线**

> 增量模式的产物始终是**该页面全量用例**，沉淀后按 `(biz_module, page)` 维度覆盖最新基线。

### 资产沉淀使用

1. 生成结果确认无误后，在「沉淀管理」下拉选择沉淀类型
2. 点击「确认沉淀」按钮完成沉淀
3. 后续同模块生成时，会自动语义召回沉淀的资产，提升生成质量

## 七、扩展指南

### 1. 新增业务模块

零代码扩展，仅需修改前端配置：

```
// frontend/src/App.js
const MODULE_LIST = [
  { value: 'merchant', label: '商户模块' },
  { value: 'secret-key', label: '密钥模块' },
  { value: 'bin', label: '卡BIN模块' },
  { value: 'payment', label: '支付模块' }, // 新增模块
];
```

同时在对应 Skill 的 `references` 目录下添加该模块的业务规则文档，重启后端即可生效。

### 2. 新增生成 Skill（扩展能力类型）

以新增「接口测试用例生成 Skill」为例：

1. 后端 `app/scripts/` 下新建 `api_test_cases.py`，继承 `BaseSkill`
2. 实现接口测试专用的 Prompt 模板与输出解析逻辑
3. 在 `flow_scheduler.py` 中新增对应执行方法
4. 前端新增对应模式与交互入口

### 3. 扩展 AI 自动化接口测试

在现有用例生成基础上扩展执行能力：

- **生成层**：新增接口测试 Skill，输出标准 Pytest 用例代码，包含请求参数、断言逻辑
- **执行层**：对接 Python + Requests/Pytest 框架，生成的用例可直接运行
- **结果层**：自动收集执行结果，回填到平台，生成测试报告
- **进阶**：支持自动同步接口文档（Swagger/OpenAPI），基于接口定义自动生成负例、边界用例

### 4. 扩展 AI 性能测试

- **场景生成**：基于业务需求生成性能测试场景，包括并发数、压测时长、混合比例
- **脚本生成**：自动生成 JMeter JMX 脚本或 Locust Python 脚本
- **执行调度**：对接压测集群，一键发起压测，自动收集 TPS、响应时间、错误率指标
- **瓶颈分析**：大模型结合监控数据，自动分析性能瓶颈并给出优化建议

### 5. 扩展 AI UI 测试

- **用例生成**：基于页面原型 / 截图 + 需求描述，生成 UI 测试用例，包含元素定位、操作步骤、预期结果
- **脚本生成**：自动生成 Playwright/Selenium 自动化脚本，支持多浏览器执行
- **智能校验**：结合视觉 AI，支持页面布局、样式、文案的智能断言
- **自愈能力**：页面元素变更时，AI 自动修正定位表达式，降低脚本维护成本

### 6. 接入其他大模型

- 后端 `llm_client.py` 为统一封装层，新增模型只需实现对应客户端
- 支持接入本地私有化模型，满足数据安全要求
- 支持多模型路由，不同场景自动匹配最优模型（轻量模型做简单生成，重度模型做复杂评审）

### 7. 其他扩展方向

- **团队协作**：新增用户体系、项目空间、权限管理
- **版本管理**：用例版本对比、需求变更差异分析
- **缺陷联动**：对接缺陷管理平台，自动生成缺陷单
- **统计看板**：生成效率、覆盖率、沉淀资产量等数据统计

## 八、常见问题

### Q：生成的用例不符合业务规则怎么办？

A：可以通过两种方式优化：1）补充业务规则后重新生成；2）将修正后的用例沉淀到项目历史库，后续生成会自动复用正确规则。

### Q：上传图片后生成结果没有识别图片内容？

A：当前版本默认不包含 OCR 能力，图片类需求建议将核心规则补充到需求描述中。如需自动识别，可接入百度 OCR / 腾讯云 OCR / 本地 PaddleOCR，在文档解析层添加图片识别逻辑。

### Q：Excel 导出打开乱码？

A：当前版本已修复该问题，导出接口返回二进制流，前端自动处理为.xlsx 格式。如仍有问题，请确认导出接口 `responseType` 设置为 `blob`。

### Q：沉淀的资产多久生效？

A：沉淀到项目历史库实时生效；沉淀到通用技能库会自动重载知识库，立即生效。
